# 完整博客管理后台设计

## 目标

将现有 Firefly 在线后台扩展为可完整管理博客内容、媒体、页面、站点配置、发布、安全与审计的统一管理系统。管理员日常操作不需要修改代码、执行本地命令或进入 GitHub 与 Cloudflare 控制台，同时保留 Astro 静态站点的访问速度、SEO、版本历史和低成本部署优势。

## 设计原则

- 常用操作简单，危险操作明确，失败可以恢复。
- GitHub 是公开博客内容与构建配置的最终事实源。
- D1 保存后台工作状态，R2 保存媒体文件。
- 后台只能修改经过 Schema 校验的结构化数据和白名单仓库路径。
- 新内容不得隐式覆盖 GitHub 中未绑定的已有文件。
- 外部服务调用不能伪装成数据库事务，所有部分成功必须可识别、可对账、可重试。
- 前端表单、API DTO 和数据库 Row 分离。
- 后台模块按职责拆分，新增字段或内容类型时不需要修改单体应用。

## 总体架构

```text
/admin 后台
  → 同源 API、Session、CSRF、Origin 与权限校验
Cloudflare Pages Functions
  ├─ D1：草稿、修订、发布任务、会话、审计、媒体引用、配置变更集
  ├─ R2：封面、正文图片、相册图片与允许的附件
  └─ GitHub Gateway：受控写入内容和配置白名单
       → Cloudflare Pages 自动构建
       → pages.dev 公开博客
```

采用混合模式：会影响静态站点的文章、页面和配置经后台生成受控文件并提交 GitHub；会话、草稿、任务状态和审计等运行数据保存在 D1；图片保存在 R2。公开博客不依赖 D1 才能访问。

## 数据所有权

### GitHub

保存已发布文章、独立页面、友链、相册、导航、侧栏、主题和其他构建配置。每次发布都有 Git 历史，可以查看差异和回滚。

### D1

保存管理员、会话、登录限制、草稿、已发布内容绑定、发布任务、媒体元数据、媒体引用、配置变更集、部署状态缓存和审计日志。

### R2

保存公开媒体对象。对象使用不可预测的随机键，D1 记录其生命周期、展示信息和引用关系。

## 后台信息架构

```text
仪表盘
内容
  ├─ 文章
  ├─ 页面
  ├─ 友链
  ├─ 相册
  └─ 公告
媒体库
站点设置
发布中心
安全与审计
```

后台采用 URL 路由保存模块、筛选条件和当前资源 ID。桌面端使用固定侧栏，移动端使用抽屉导航。列表共享搜索、筛选、分页、加载、空状态和错误恢复模式。

## 仪表盘

仪表盘展示草稿、已发布文章、媒体和页面数量，最近编辑和发布记录，GitHub、D1、R2 与 Cloudflare 健康状态，以及发布失败、待对账和孤立媒体等待处理事项。提供写文章、上传图片和管理站点快捷入口，不添加无业务价值的图表。

## 文章管理

文章中心统一管理草稿、修订稿和已发布文章，支持：

- 新建、编辑、复制、预览、发布、撤回和删除。
- 搜索、分页以及按状态、标签和分类筛选。
- 自动保存、手动保存和离开未保存页面保护。
- 封面上传、正文拖拽与粘贴图片。
- 发布前校验标题、slug、日期、摘要、图片引用和敏感信息。
- 已发布文章继续修订，不直接修改线上版本。
- slug 重命名按路径迁移处理。
- GitHub 版本历史、差异查看和回滚。
- 导入 GitHub 已有文章并建立后台绑定。
- Markdown 编辑、分屏预览和全屏预览。

MDX 默认以只读或受限方式管理，不允许后台执行任意 import、组件或脚本。加密文章使用独立安全模型，文章密码不得作为普通明文字段在 D1、API 或日志中传播。

## 内容身份与并发控制

每个内容资源使用不可变 `content_id`，slug 仅作为可修改公开路径。D1 绑定记录至少包含：

```text
content_id
github_path
github_blob_sha
last_commit_sha
version
sync_status
```

新文章首次发布时，如果目标 GitHub 路径已经存在，发布返回冲突并要求导入或更换 slug，绝不携带远端 SHA 自动覆盖。已绑定文章只有在远端 SHA 与预期一致时才允许更新。保存操作携带版本号，两个标签页或设备并发编辑时返回冲突而不是后写覆盖。

## 页面与结构化内容

后台提供专用管理模块覆盖：

- 关于我
- 友链
- 赞助
- 相册
- 公告
- 留言板配置
- 工具页
- 更新日志
- 动态或说说
- 首页介绍
- 自定义静态页面

每种内容有专用结构化 Schema 和表单。允许使用 Markdown 的位置可以切换源码编辑，但后台不提供任意 Astro、Svelte 或 TypeScript 编辑能力。

## 站点配置

配置按用途分组：

- 基础信息：名称、描述、语言、站点地址、头像。
- 导航与侧栏：菜单、排序、显示条件和小组件。
- 首页与文章：布局、分页、封面、版权和评论。
- 外观：主题、壁纸、字体和特效。
- 社交与页脚：社交链接、备案、运行时间。
- 集成：评论、统计、音乐、PlantUML 等。
- SEO：Open Graph、站点地图、搜索和 RSS。

覆盖现有 `src/config` 中的站点、资料、导航、侧栏、页脚、公告、友链、相册、赞助、评论、统计、壁纸、特效、封面、版权、音乐、字体、代码高亮、Pio、PlantUML 和首页介绍配置。

保存设置只生成 D1 变更集。管理员可以查看差异并一次发布多项设置，避免每次切换开关都触发构建。服务端使用每类配置的固定序列化器生成白名单文件，不接受前端提供仓库路径或任意源代码。

## 媒体管理

媒体生命周期为：

```text
上传中 → 可用 → 使用中 → 回收站 → 已清理
```

媒体库支持上传、搜索、分页、复制链接、查看尺寸和格式、设为封面、插入内容、查看引用、替换和批量清理未引用媒体。使用中的媒体不能直接删除；删除先进入回收站并允许恢复，经过保留期后才物理清理。

R2 成功而 D1 写入失败时，系统记录待清理对象并自动重试。替换媒体保留旧对象以支持内容回滚。需要快速撤回的媒体不使用一年 immutable 缓存策略。

## 发布状态机

每次发布生成唯一、幂等的任务。重复点击同一操作不会创建重复提交。任务记录资源、预期版本、目标路径、请求内容摘要、状态、重试次数、GitHub commit SHA、部署状态和失败原因。

正常状态：

```text
待校验 → 发布中 → GitHub 已提交 → 等待 Cloudflare → 已上线
```

异常状态：

```text
校验失败
内容冲突
提交失败
待对账
构建失败
已回滚
```

GitHub 成功但 D1 状态更新失败时，任务进入待对账，不显示为普通发布失败。对账服务根据 commit SHA、目标路径和内容摘要恢复绑定与任务状态。Cloudflare 构建失败不会撤销 GitHub 提交，后台提供查看原因、重新构建和回滚入口。

## 后端模块边界

请求链路：

```text
HTTP Handler
  → Admin 安全包装器
  → Application Service
  → D1 Repository / GitHub Gateway / R2 Gateway
```

核心模块：

- `ContentService`：草稿、修订、导入和内容版本。
- `PublishService`：校验、提交、幂等任务和对账。
- `SiteConfigService`：配置 Schema、变更集和受控序列化。
- `PageService`：独立页面和结构化内容。
- `MediaService`：上传、引用、替换、回收站和清理。
- `DeploymentService`：Cloudflare 构建状态和重试。
- `SessionService`：会话、设备和吊销。
- `AuditService`：安全与资源操作记录。

数据库 Row、API DTO 和前端 Form Model 分开定义。列表接口返回摘要 DTO，详情接口按需返回正文，避免草稿列表加载所有内容。

## 安全模型

- Session 使用 HttpOnly、Secure、SameSite Cookie，服务端只存 Token 哈希。
- 所有变更请求校验 CSRF 和允许来源。
- D1 只使用参数化 SQL。
- GitHub 写入限制到明确白名单，禁止路径穿越和任意代码写入。
- R2 上传校验大小、扩展名、MIME 和文件魔数。
- 登录使用限速、锁定和审计。
- 修改密码、删除内容、回滚和发布配置要求二次确认；高风险操作要求重新验证密码。
- Token 与 Secret 仅存在于 Cloudflare Secret，不写入仓库、D1 明文、前端响应或日志。
- PBKDF2 验证兼容旧迭代参数，登录成功后按当前策略逐步重新哈希。
- Session 支持设备列表、单设备吊销和全部注销。
- 审计记录请求 ID、操作者、资源类型、资源 ID、动作、结果、时间和必要的非敏感上下文。

## 错误契约

API 错误统一包含：

```text
code
message
fieldErrors
retryable
requestId
```

处理规则：

- `401`：跳转登录并保留当前后台地址。
- `403`：提示权限或重新验证要求。
- `409`：展示内容差异或版本冲突，不覆盖。
- `422`：定位到具体字段。
- `429`：显示限速等待信息。
- 外部服务失败：保留本地编辑内容，并提供重试、对账或恢复入口。

面向用户的消息不暴露堆栈、SQL、Token、内部路径和第三方响应中的敏感信息。

## 交付阶段

### 阶段一：平台基础与最高风险修复

- 拆分后台骨架和 URL 路由。
- 建立 DTO、统一错误格式和安全包装器。
- 修复未绑定新草稿覆盖同 slug GitHub 文件的问题。
- 实现发布任务状态机、幂等与对账。

### 阶段二：完整文章管理

- GitHub 已有文章导入。
- 草稿、修订和已发布文章统一列表。
- 搜索、筛选、分页和详情按需加载。
- 自动保存、并发冲突和离开保护。
- 修订、重命名、撤回、删除、历史和回滚。

### 阶段三：媒体与页面管理

- 媒体引用、回收站、恢复和可重试清理。
- 页面、友链、相册、公告和赞助管理。

### 阶段四：全站设置管理

- 配置 Schema、变更集和差异预览。
- 白名单文件生成、批量发布和版本恢复。

### 阶段五：部署、安全与审计

- Cloudflare 部署追踪和重新构建。
- Session 与设备管理。
- 密码哈希升级。
- 审计查询、健康检查和恢复工具。

## 验证策略

每个阶段运行：

```text
pnpm check
pnpm type-check
pnpm lint
pnpm build
```

功能与安全验证覆盖：

- 未认证、会话过期、CSRF、Origin 和登录限速。
- 参数化 SQL、路径白名单和恶意上传。
- 同 slug、并发保存和 GitHub SHA 冲突。
- GitHub、D1、R2 的部分成功、重试和对账。
- Cloudflare 构建成功、失败和回滚。
- 桌面、移动端、深色模式和 reduced-motion。
- 刷新、返回、后台深链接和未保存离开保护。

## 完成标准

- 管理员可以仅通过 `/admin/` 管理博客已有内容和设置，不需要修改代码或运行本地命令。
- 未绑定内容不能覆盖 GitHub 现有文件。
- 发布和媒体操作的部分失败都能被识别并恢复。
- 已发布内容和配置具有差异、版本与回滚能力。
- 后台不暴露任意代码、路径、SQL 或 Secret 编辑能力。
- 公开博客继续通过 Cloudflare Pages 静态构建稳定访问。
- 后台模块边界清晰，新增内容字段或配置类型只需扩展对应 Schema、服务和表单模块。
